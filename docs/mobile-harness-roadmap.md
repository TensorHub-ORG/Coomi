# 手机版（Coomi Android）更新方案 · 基于「模型 + Harness」能力清单

> 状态：规划稿（2026-09-29）。落地顺序见 M1–M5；桌面端已完成的改动会直接成为手机端的共同底座。

## 0. 现状（代码事实）

| 层 | 现状 |
|---|---|
| 壳 | `apps/coomi-app`：Termux 派生的 Android 工程（`com.termux.app.*` + `app.coomi.*`）。`CoomiService` 拉起/守护引擎子进程，`CoomiEngineMonitor`、`CoomiIslandHelper`（通知/岛屿）、`RootAccessController`/`ShizukuAccessController`、`CoomiLocalModelsActivity`、备份与 `CoomiAutoBackupWorker`、`UpdateChecker`、群与协作 Activity |
| 引擎 | 同一份 `coomi-rs`（Android 交叉编译）。`serve --home --port --token --cwd --static-dir --inbox`；`engine.version` 指纹保证 APK 与引擎一致 |
| UI | `apps/web`（Vue 3 + Pinia）：聊天气泡/时间线/工具卡/推理块/审批 Sheet/提问 Sheet/模型选择/群聊/协作；构建产物打成 `assets/web.zip` 由引擎 serve |
| 运行时 | `assets/runtime-v2-manifest.json` = proot Debian 运行时，给 Agent 提供 Linux 工具环境 |
| 已有移动专属能力 | 前台服务常驻、通知/岛屿、本地模型入口、root/Shizuku、自动备份 |

**定位结论**：手机不是桌面的缩小版，而是「**随身 Harness 端**」——随时在线、有通知/传感器/本地模型、能拿到人的即时审批。方向是让 Harness 在手机上做到「低功耗、可中断、可恢复、成本可控」。

## 1. 三条主线

1. **契约先行**：工具契约、检索、编排、审批、轨迹采集全部与桌面共用引擎协议，手机只做**策略差异化**（预算、并发、沙箱、通知）。
2. **成本/耗电是一等指标**：token、流量、电量写成硬预算，Harness 每次决策都在预算内取舍。
3. **人在环是手机的优势**：审批、提问、停止、插话从「弹窗」升级为**通知即审批门**（锁屏可操作、超时可降级）。

## 4. 分阶段路线

**M1 · 契约与预算先行（P0）**
交付：工具契约 v2（含移动工具族：通知/分享/文件/日历）；三方协议版本对齐；Harness 预算结构（token/流量/电量/并发）进引擎配置。
验收：新旧 APK 都能连同一引擎；「全量注入 → 按需注入」可切换；超预算有明确降级行为。

**M2 · 检索与动态注入（P0）**
交付：工具索引（名称/描述/Schema/示例/历史成功率）+ 端上小检索 + Top-k/阈值/触发条件；上下文预算按模型窗口与手机档位自适应。
验收：工具数 35 → 200+ 时注入 token 不线性增长；成功率不降。

**M3 · 编排与审批门（P0/P1）**
交付：规划/执行分离；Lead + Subagent 职责与工具约束；检查点 + 恢复（含被系统杀死）；审批门接入通知/岛屿（锁屏可批、超时降级、危险操作二次确认）。
验收：锁屏审批可用；切后台 10 分钟回来状态正确；被杀后能续跑。

**M4 · 记忆、安全与数据闭环（P0/P1）**
交付：短/长记忆分离 + 端上小库；权限↔工具许可映射；审计日志与轨迹采集（失败样本、审批记录）；上传开关 + 脱敏管道。
验收：跨会话延续可用；敏感数据默认不出机；轨迹能在桌面端回放并归因到模型/Harness/工具/数据。

**M5 · 评估与联合迭代（P1）**
交付：移动场景基准（弱网/后台/打断/低电）+ 指标看板 + 回归与 A/B + 「模型×Harness」联合调参流程。
验收：每次模型切换都有可比的移动端评测；失败能自动归因。

## 5. 手机版专属建设项（清单未列但必须有）

1. **后台与 Doze 策略**：前台服务 + 任务检查点 + 被杀可续跑（属编排层需求，不是壳补丁）
2. **通知即审批门**：审批/提问/停止进通知与岛屿，锁屏可操作、超时降级
3. **权限即能力**：Android 权限 → 工具许可矩阵（无权限则工具不可见/只读）
4. **沙箱分级**：proot（默认）→ root/Shizuku（显式开启 + 二次确认 + 审计）
5. **双轨模型**：端侧小模型（离线/隐私/免费）与云模型（强能力/花钱）按网络与电量自动切换
6. **弱网与断网**：请求重放、增量落盘、离线继续规划
7. **体积与分发**：APK 体积、ABI 裁剪、`web.zip` 热更与引擎二进制指纹一致性（机制已有，纳入发布流程）
8. **隐私合规**：数据分级、上传开关、审计导出

## 7. 需要拍板的三件事

1. **手机端默认模型**：默认端侧（省流量/隐私好/能力弱）还是默认云（能力强/花钱）？
2. **系统能力工具默认开放度**：通知/文件/分享/日历这类「能改用户数据」的工具默认开还是默认关（按需授权）？
3. **root / Shizuku 是否允许 Agent 调用**：允许（能力最强、风险最高、需审计）还是仅人工操作？
